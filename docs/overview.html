    Why this stack
    Each tool solves a distinct problem. Understanding why each layer exists makes the whole system easier to reason about, debug, and extend.
    🐳
    Docker
    packaging · isolation · reproducibility
    The problem it solves: "It works on my machine" — code behaves differently across developer laptops, staging servers, and production because the environment (OS packages, PHP version, system libs) differs. Docker packages the application and its entire runtime into a single immutable image that runs identically everywhere.
    Use it when
    You need the same binary to run locally, in CI, and in production without manual environment setup.
    Don't skip it when
    Tempted to install PHP directly on a server — you lose reproducibility and can never roll back cleanly.
    Key concept
    Multi-stage builds: a fat "builder" image compiles code, a lean "runtime" image ships only what runs. Smaller attack surface, faster pulls.
    🖥
    Docker Compose
    local orchestration · wiring · dev experience
    The problem it solves: Running multiple containers that need to talk to each other (nginx → php → mysql) requires networking, volume mounts, env vars, and startup ordering. Compose declares all of that in one file so a new developer can start the whole stack with a single command.
    Use it when
    Running locally or in CI for integration tests. It is not for production — it lacks scheduling, self-healing, and scaling.
    Override file pattern
    docker-compose.override.yml adds dev-only config (bind mounts, debug ports) that never reaches production images.
    Stop using it when
    You need replicas, rolling updates, secrets management, or cross-host networking — that is Kubernetes territory.
    ☸
    Kubernetes
    scheduling · self-healing · scaling · secrets
    The problem it solves: In production, containers crash, nodes fail, traffic spikes, and deploys need zero downtime. Kubernetes is the control plane that keeps your desired state running — if a pod dies, it restarts it; if traffic doubles, HPA adds replicas; if a deploy breaks, it stops rolling and holds.
    The core idea — desired state: You declare what you want (3 replicas, this image, these env vars), and Kubernetes continuously reconciles actual state toward that. You never SSH into a server and run commands. You change a YAML file.
    Deployment
    Rolls updates one pod at a time (maxUnavailable 0). If the new image fails its health check, the rollout stops automatically.
    StatefulSet
    For MySQL — gives each pod a stable identity and its own PVC. Unlike a Deployment, pods are not interchangeable; pod-0 always gets the same disk.
    HPA
    Watches CPU/memory metrics and adds or removes pod replicas automatically. Production scales 3→20 replicas based on load.
    Sidecar pattern
    nginx and php-fpm run in the same Pod, sharing localhost. No service hops for FastCGI, no extra latency, no separate network policy.
    ⎈
    Helm
    templating · versioning · environment config
    The problem it solves: Kubernetes YAML is verbose and repetitive. Staging and production share 95% of the same config but differ on replica count, image tag, storage size, and TLS. Without Helm you either duplicate all that YAML or write custom scripts. Helm turns the 5% that varies into variables and lets you render environment-specific manifests from a single chart.
    Values cascade: values.yaml (defaults) ← values-staging.yaml (overrides) — Helm deep-merges them. You only write what changes, and the chart never diverges between environments.
    Use it when
    You have more than one environment, more than one resource type, or want to version your infrastructure the same way you version code.
    helm lint / helm template
    Renders the chart locally without touching a cluster. The PR gate runs this on every pull request so broken YAML never reaches git main.
    Helm vs. plain YAML
    Plain YAML is fine for one environment. Two or more environments with shared structure → use Helm or you'll spend your time copy-pasting and diffing.
    🔄
    ArgoCD
    GitOps controller · drift detection · auditability
    The problem it solves: Without GitOps, someone runs kubectl apply manually, the cluster drifts from what's in git, and nobody knows what version is actually running or who changed what. ArgoCD makes git the single source of truth — it polls your repo every 3 minutes and reconciles the cluster to match. If someone manually edits a resource, ArgoCD reverts it (on staging) or flags the drift (on production).
    Why not just CI deploy? CI pipelines push deploys (kubectl apply in a workflow). ArgoCD pulls — the cluster fetches its own desired state. Pull-based is more secure (no cluster credentials in CI), resilient (works if CI is down), and self-healing (continuously re-applies, not one shot at deploy time).
    Staging — auto-sync
    Every git commit to main reaches staging within ~3 min automatically. Developers see their change live immediately without doing anything.
    Production — manual sync
    An operator reviews what will change (ArgoCD shows a diff) and deliberately clicks Sync. The sync window also blocks Friday–Monday deploys.
    Image Updater
    Watches GHCR for new image tags matching a pattern. When CI pushes a new SHA, Updater commits the new tag back to values-staging.yaml, closing the loop without CI needing cluster access.
    AppProject
    RBAC boundary: restricts which git repos, which destination namespaces, and which resource types ArgoCD is allowed to manage. Prevents one app from touching another's namespace.
    ⚡
    How it all connects — the GitOps loop
    the full developer → production journey
    Git is the control plane for everything. No human ever touches a production server directly. The loop is fully automated from commit to staging; production requires one deliberate human decision.
    developer
    1. Write code, run locally
    Docker Compose gives a full-stack environment in one command. Nginx, PHP, MySQL all behave the same as they will in production — same nginx config, same PHP version, same env var names. No "works on my machine" surprises.
    on PR open
    2. CI validates the Helm chart
    helm-lint.yml renders the chart against all 3 value sets and validates the YAML with kubeval. A broken template or wrong value type is caught before merge, not after deploy.
    on merge to main
    3. CI builds and publishes the image
    build-push.yml runs a multi-stage Docker build, pushes the image to GHCR tagged with the commit SHA, then commits the new tag into values-staging.yaml. The cluster never needs to pull from CI — it pulls from the registry.
    ~3 min later
    4. ArgoCD syncs staging automatically
    ArgoCD detects the SHA change in git, renders the Helm chart with staging values, and applies the diff to linexa-staging. Kubernetes rolls the update one pod at a time. Health checks gate the rollout — a bad image stops here, not in production.
    operator decision
    5. Promote to production — manually
    After validating staging, an operator opens ArgoCD, inspects the diff (what changes, which image, which config), and clicks Sync. The sync window prevents this outside business hours. HPA then scales production 3→N replicas based on traffic.

    What Terraform does
    Terraform's job is simple: describe infrastructure as code, apply it once, never touch the GCP console manually. You write what you want → terraform apply → GCP has it. Change the code → terraform apply again → GCP matches. terraform destroy → everything gone, billing stops.

    What gets created — in order
    step 1
    Enable GCP APIs
    Activates container.googleapis.com (GKE) and compute.googleapis.com (VMs + networking) on the project. New GCP projects have most APIs disabled by default — Terraform enables them before trying to create resources that need them.
    step 2
    VPC: linexa-vpc + linexa-subnet
    Why not use the default VPC? GCP's default VPC is shared across your whole project — anything else you build lives on it too. A dedicated VPC isolates linexa's traffic completely.

    The subnet has three CIDR ranges:
    • 10.0.0.0/20 — the node VMs themselves
    • 10.48.0.0/14 — pods (VPC-native: each pod gets a real GCP IP, no NAT)
    • 10.52.0.0/20 — K8s services (ClusterIPs map to this range)
    step 3
    GKE cluster: linexa
    SettingValueWhy
    private_nodestrueNode VMs have no public IPs — not reachable from internet even if someone guesses the address
    private_endpointtrueK8s API server has no public IP — reachable only from inside the VPC via the IAP bastion
    master_authorized_networks10.0.0.0/20Only the bastion subnet can reach the private master endpoint
    workload_identityenabledPods can act as GCP service accounts without a JSON key file stored anywhere
    ip_allocationVPC-nativePods get real IPs from the subnet — direct routing, no overlay network overhead
    step 5
    Node pool: 1 × e2-standard-2
    2 vCPU / 8 GB RAM. The full dev stack — app (nginx + php-fpm, ~0.1 vCPU / 128 Mi), mysql-0 (~0.2 vCPU / 512 Mi), system pods (~0.3 vCPU / 300 Mi) — uses ~0.6 vCPU / ~1 GB total. One e2-standard-2 is already 3× oversized. Add a second node when you need pods on separate machines for fault tolerance.

    COS + containerd — Container-Optimized OS, no Docker daemon, smaller attack surface.
    Shielded VM — Secure Boot + integrity monitoring.
    Auto-repair + auto-upgrade — GKE replaces unhealthy nodes and patches the OS automatically.
    The three commands
    # 1 — download Google provider plugin (~30 MB) + set up .terraform/ terraform init # 2 — preview: calls GCP APIs, compares desired vs actual, prints a diff # nothing is created — safe to run anytime terraform plan # 3 — executes the plan, creates all 4 resources, takes ~5 min # prints outputs at the end including the kubectl get-credentials command terraform apply
    State file
    After terraform apply, Terraform writes terraform.tfstate locally. This file maps your code to real GCP resource IDs — it's how Terraform knows what to update or destroy on the next run. If you lose it, Terraform loses track of what it created.
    For a team: store state in GCS so everyone shares the same view. Uncomment the backend "gcs" block in versions.tf and create a bucket: gsutil mb gs://replenit-lab-tfstate
    Teardown
    # deletes cluster, node pool, VPC, subnet in reverse order (~3 min) # billing stops immediately after terraform destroy

    At a glance — who does what
    Helm Template engine. Takes templates/ + values.yaml + values-dev.yaml → outputs plain Kubernetes YAML. Never talks to the cluster. You never run it manually. ArgoCD GitOps controller running inside the cluster. Every 3 min: pulls git → calls Helm → diffs output vs cluster → applies only what changed. CI (GitHub Actions) Builds the Docker image on every push, pushes it to GHCR, then commits the new image SHA into values-dev.yaml. That commit is what ArgoCD detects.
    The loop: you push code → CI builds image + bumps SHA in values-dev.yaml → ArgoCD detects the file change → Helm re-renders → kubectl apply → new pods roll out.
    You touch nothing after the push. For production: ArgoCD sees the diff but waits — you click Sync when ready.
    Helm — template engine
    Helm knows nothing about your cluster. It takes your templates + values files and produces plain Kubernetes YAML. Its job ends there — it does not apply, watch, or care what happens next.
    # templates contain placeholders helm/control-plane/templates/deployment.yaml → replicas: {{ .Values.app.replicaCount }} helm/control-plane/values.yaml → replicaCount: 2 (default) helm/control-plane/values-dev.yaml → replicaCount: 1 (override) # Helm merges them and outputs pure K8s YAML: spec: replicas: 1 containers: - image: ghcr.io/brabia/linexa:sha-abc1234
    You never run helm install yourself — ArgoCD owns that. You only touch Helm files (templates, values) to change what gets deployed.
    ArgoCD — GitOps controller
    ArgoCD runs inside your cluster and does three things on a loop every 3 minutes:
    1. git pull github.com/brabia/gitops (main) 2. helm template helm/control-plane -f values.yaml -f values-dev.yaml 3. kubectl apply <diff between rendered YAML and what's in the cluster>
    Cluster = git
    If someone runs kubectl edit manually, ArgoCD reverts it on the next cycle. Git is the only source of truth.
    selfHeal
    Dev only. Any drift from git (manual edit, crashed pod config) is automatically corrected without human action.
    Manual sync
    Production. ArgoCD detects the diff but waits. An operator reviews it in the UI and explicitly clicks Sync.
    AppProject
    RBAC boundary — restricts which repos, namespaces, and resource types ArgoCD can touch. Prevents apps from interfering with each other.

    How do you decide how many nodes?
    A node is a VM. A replica is a copy of a pod. They are independent — 1 node can run many pods, and many replicas can all run on the same node.
    You size nodes around what your pods actually consume:
    e2-standard-2 = 2 vCPU / 8 GB RAM your pods (dev): app (nginx + php-fpm) ~ 0.1 vCPU / 128 Mi mysql-0 ~ 0.2 vCPU / 512 Mi system (kube-proxy…) ~ 0.3 vCPU / 300 Mi ───────────────────── total ~ 0.6 vCPU / ~1 GB # 1 node is 3× oversized already
    1 node — dev ✓
    All pods fit. If the node crashes the env goes down — acceptable for dev.
    2 nodes — prod app
    Spread replicas: 2 across machines. A node failure keeps the app alive.
    3+ nodes — stateful prod
    No single node failure takes a quorum. Required for HA databases.
    Rule: start at 1, add a node when you hit ~70% CPU or RAM, or when you need replicas on separate machines for fault tolerance.

    We are going to create a dedicated Kubernetes namespace for the dev environment. A namespace is a logical boundary inside the cluster — it isolates resources (pods, services, secrets) from other namespaces. Without it, everything would land in default, making it impossible to apply per-environment policies or delete cleanly.

    k8s/namespaces/dev.yaml creates three objects: the Namespace itself, a ResourceQuota capping CPU/memory so a misbehaving pod can't starve the node, and a LimitRange setting default requests/limits on containers that don't declare their own.

    ① Namespace
    A logical isolation boundary named linexa-dev inside the shared cluster. All pods, services, and secrets live inside it — invisible to other namespaces. Label pod-security.kubernetes.io/enforce: baseline blocks privileged containers at admission.
    ② ResourceQuota
    Namespace-wide ceiling. If the total across all pods hits the limit, new pods are rejected. Prevents a runaway deployment from eating the whole cluster node.
    requests.cpu 2 · requests.memory 2Gi · limits.cpu 4 · limits.memory 4Gi · pods 20 · PVCs 5
    ③ LimitRange
    Per-container defaults. If a container spec omits resources:, Kubernetes injects these values automatically. Without it, a container with no resource spec gets unlimited CPU — the node killer.
    default limit: 250m CPU / 128Mi · default request: 50m CPU / 64Mi

    How Helm finds deployment.yaml and the other templates
    You never reference them by name. Helm scans templates/ and renders every .yaml file it finds there — filling in {{ .Values.* }} from your values files, then sending the result straight to the Kubernetes API.
    helm/control-plane/ ├── Chart.yaml identity file — name, version; Helm won't load the dir without it ├── values.yaml base defaults — always loaded first ├── values-dev.yaml env overrides — merged on top with -f flag └── templates/ ← Helm renders ALL .yaml files in here ├── deployment.yaml ✓ rendered + applied ├── service.yaml ✓ rendered + applied ├── ingress.yaml ✓ rendered + applied (skipped if ingress.enabled: false) ├── backend-config.yaml ✓ rendered + applied (skipped if ingress.enabled: false) └── configmap.yaml ✓ rendered + applied (skipped if nginx.config is empty)
    deployment.yaml
    The running app. Tells Kubernetes: spin up replicaCount pods, each running image.repository:image.tag from your values. CPU and memory limits are set here too. The {{- if .Values.nginx.config }} block is an optional escape hatch — if you set nginx.config in values it mounts a ConfigMap over the baked-in nginx config at runtime. Currently unused.
    service.yaml
    Makes the pods reachable inside the cluster. A Service is a stable address that load-balances across all pods matching app: {{ .Release.Name }}. In dev it is NodePort — GKE's GCE Ingress controller requires NodePort to route traffic into the cluster. The cloud.google.com/backend-config annotation is only added when ingress.enabled: true — it links this Service to the BackendConfig so GKE knows to attach Cloud Armor.
    ingress.yaml
    The entry point from the internet. The entire file is skipped when ingress.enabled: false. When enabled, kubernetes.io/ingress.class: gce tells GKE's ingress controller to provision a real GCP HTTP(S) LB. The staticIpName annotation pins it to the pre-reserved linexa-dev-ip so the IP stays stable across helm uninstall / reinstall cycles.
    backend-config.yaml
    GKE-specific custom resource (cloud.google.com/v1beta1) — plain Kubernetes knows nothing about it. It wires Cloud Armor to the LB backend. Also conditional on ingress.enabled. When cloudArmor.enabled: true it adds a securityPolicy block pointing to linexa-dev-allowlist. When false, the resource still exists but is empty — GKE requires it to be present whenever the Service carries the BackendConfig annotation, even with no policy attached.
    configmap.yaml
    Only rendered if nginx.config is set in values — it is "" by default so this file produces nothing. Its purpose: if you need to change the nginx config without rebuilding the Docker image, set nginx.config: | in values and Helm creates this ConfigMap. The deployment.yaml mounts it over /etc/nginx/conf.d/default.conf at runtime, overriding the baked-in config.
    The file names don't matter to Helm — what matters is the kind: field inside each file. You could rename deployment.yaml to app.yaml and it would work identically. MySQL is not in this chart — the control-plane is stateless (php-fpm + nginx only). MySQL lives in Docker Compose for local dev and would be a separate chart if added to GKE.

    The outermost boundary. Every resource in this diagram — the Load Balancer, the GKE cluster, the GCE Persistent Disk — lives inside one GCP project and rolls up to one billing account. IAM service accounts attached to the GKE node pool let the cluster pull images from GHCR, write logs to Cloud Logging, and provision GCE disks on behalf of PersistentVolumeClaims. VPC firewall rules are also project-scoped.
    GCP Load Balancer — global HTTP(S) LB, provisioned by the Ingress controller
    Not a Kubernetes object — a GCP cloud resource created automatically. When you ran kubectl apply on the Ingress manifest, GKE's built-in Ingress controller called the GCP API and provisioned: a forwarding rule (public IP), a backend service, a URL map, and a health check. You never created the LB directly — Kubernetes manages its full lifecycle. Deleting the Ingress triggers GCP to delete the LB and release the IP.
    GCE Persistent Disk — block storage backing the PersistentVolume, cluster-level GCP resource
    A GCP block device — the actual physical disk your MySQL data lands on. Created automatically by the standard-rwo StorageClass when the PVC was first bound. Lives entirely outside any K8s namespace; it's a project-level GCP resource. The PersistentVolume is just a K8s pointer to this disk. Annotated helm.sh/resource-policy: keep so helm uninstall does not delete it — your database survives a full chart teardown.
    ☸ Kubernetes — Ingress & Routing
    Ingress — K8s object, namespace-scoped; programs the GCP LB's routing rules
    A namespaced Kubernetes resource — the bridge between GCP's Load Balancer and your Services. Defines host/path rules: "if Host: dev.linexa.eu, route all paths to Service linexa-dev-app:80." GKE's Ingress controller reads this object and updates the GCP URL map accordingly. One Ingress can route multiple hostnames to different backends — no extra LB cost.
    Service · linexa-dev-app ClusterIP :80 — stable virtual IP for the app pods
    Pods are ephemeral — every restart gives them a new IP. A ClusterIP Service gives the Ingress backend a permanent address. kube-proxy (a DaemonSet process on every node) writes iptables rules that translate the ClusterIP to a healthy pod IP. If multiple replicas exist it load-balances between them. The label selector app=linexa is the only link between the Service and its pods — no manual IP wiring.
    Service · linexa-dev-mysql ClusterIP :3306 — K8s DNS name for the database, internal only
    php-fpm connects using the hostname linexa-dev-mysql (full form: linexa-dev-mysql.linexa-dev.svc.cluster.local). CoreDNS resolves this name to the Service's ClusterIP; kube-proxy routes it to the mysql pod. This Service has no NodePort or LoadBalancer — it is unreachable from outside the cluster. Only pods inside the namespace can dial port 3306.
    ☸ Kubernetes — Workload Controllers & Pods
    Deployment → ReplicaSet — manages the stateless app pod
    You declare replicas: 1 in the Deployment spec. Kubernetes creates a ReplicaSet which continuously reconciles actual vs desired pod count — if the pod crashes, the ReplicaSet creates a replacement immediately. On every helm upgrade or image change, the Deployment creates a new ReplicaSet, brings the new pod to Ready, then terminates the old pod — zero-downtime rolling update.
    Pod · linexa-dev-app-*
    POD
    nginx container · :80
    Receives HTTP from the Service. Serves static assets directly from the image filesystem. Detects .php requests and proxies them via FastCGI to 127.0.0.1:9000 — both containers share the pod's network namespace and reach each other on localhost.
    php-fpm container · :9000
    PHP FastCGI Process Manager — executes index.php. Connects to MySQL using the K8s DNS name linexa-dev-mysql:3306. Credentials arrive as environment variables injected from the Secret — never hardcoded.
    Sidecar pattern: nginx + php-fpm share one pod so FastCGI stays on localhost — never on the network. The suffix -* is random, assigned by the ReplicaSet, and changes on every rollout.
    StatefulSet — manages the mysql pod, stable name and dedicated PVC
    Like a Deployment but for workloads that need a stable identity. Each replica gets: a fixed ordinal name (-0, -1, …), its own dedicated PVC that is never deleted when the pod is deleted, and ordered startup/shutdown. This is why the pod is named linexa-dev-mysql-0 (fixed suffix) instead of a random hash. If the pod is evicted and rescheduled to another node, the same GCE disk reattaches — data survives.
    Pod · linexa-dev-mysql-0
    POD
    mysql container · :3306
    MySQL 8.0 — single-container pod. Listens on :3306 for connections from php-fpm. All writes go to the PVC volume mounted at /var/lib/mysql. Credentials injected via Secret env vars. Managed by the StatefulSet — its name and PVC are permanently linked.
    The pod can be deleted and recreated and its data is completely safe — the PVC stays, the GCE disk stays, the next pod mounts the same volume and continues.
    ☸ Kubernetes — Storage
    PVC → PV → GCE Persistent Disk — three objects, one physical disk
    PVC (namespace-scoped) — a storage request: "I need 5 Gi, ReadWriteOnce." Kubernetes matches it against available PVs or calls the StorageClass to provision one on demand. Owned by the StatefulSet pod — deleted with the PVC it belongs to, but not by the StatefulSet controller.
    PV (cluster-scoped) — represents the actual disk as a K8s resource. Not bound to any namespace — visible to the entire cluster, but claimed by one PVC at a time. Created by the standard-rwo StorageClass provisioner.
    GCE Persistent Disk (GCP resource) — the underlying block device. When MySQL writes to /var/lib/mysql, bytes land here. The PV is only a K8s pointer to this disk — the disk itself has no awareness of Kubernetes and persists independently.
    ☸ Kubernetes — Config & Secrets
    ConfigMap — non-secret config mounted as files into containers
    nginx.conf lives in a ConfigMap. Helm renders it from a template at deploy time and applies it to the cluster. The nginx container mounts it as a file at /etc/nginx/conf.d/default.conf. Changing the ConfigMap + rolling the pod picks up a new nginx config without rebuilding or repushing the image. ConfigMaps are stored in plain text in etcd — never store passwords here.
    Secret — credentials injected as environment variables into containers
    MYSQL_ROOT_PASSWORD, MYSQL_PASSWORD, and related credentials are stored in a K8s Secret (base64-encoded in etcd). Injected into both the php-fpm and mysql containers as env entries — credentials never appear in the image, Dockerfile, or git history. ⚠ Current state: Helm values ship with changeme placeholders — replace with Sealed Secrets, External Secrets Operator, or SOPS before any shared or production environment.
    ☸ Kubernetes — Namespace & Governance
    Namespace · linexa-dev + ResourceQuota + LimitRange
    Namespace — a virtual cluster partition. All K8s objects in this diagram live inside linexa-dev. Names must be unique within the namespace. RBAC policies and NetworkPolicies are scoped here. An object in linexa-dev cannot accidentally reach objects in another namespace without explicit policy.
    ResourceQuota — caps total resource consumption for the whole namespace: max total CPU, max total memory, max number of Pods, PVCs, Services, etc. Prevents one namespace from starving the rest of the cluster.
    LimitRange — sets default CPU/memory requests and limits for individual containers that don't declare their own. Ensures every container is schedulable with predictable behavior, even when developers forget to specify resources.

    8. Update + redeploy
    After changing templates or values, re-run helm upgrade. After pushing a new image, restart the deployment to pull :latest.
    # after values or template changes helm upgrade linexa-dev ./helm/control-plane \ -f helm/control-plane/values.yaml \ -f helm/control-plane/values-dev.yaml \ -n linexa-dev # after pushing a new image kubectl rollout restart deployment/linexa-dev-app -n linexa-dev # check history / rollback helm history linexa-dev -n linexa-dev helm rollback linexa-dev -n linexa-dev
    Do I need to rebuild the image every time?
    PHP source files changed (app/src/) — Yes. Files are baked into the image at build time. Bump the version, rebuild, push, then pass the new tag to Helm.
    # bump version (on your laptop) VERSION=0.0.2 docker build -t ghcr.io/brabia/linexa:$VERSION ./app docker push ghcr.io/brabia/linexa:$VERSION # deploy the new tag (on the bastion) helm upgrade linexa-dev ./helm/control-plane \ -f helm/control-plane/values.yaml \ -f helm/control-plane/values-dev.yaml \ --set image.tag=$VERSION \ -n linexa-dev
    Helm templates or values changed — No rebuild. Just upgrade.
    helm upgrade linexa-dev ./helm/control-plane -f helm/control-plane/values.yaml -f helm/control-plane/values-dev.yaml -n linexa-dev
    Local development (Docker Compose) — Never rebuild. The bind mount makes PHP changes instant — edit a file, refresh the browser.
    volumes: - ./app/src:/var/www/html # live reload — no restart needed

    11. Test tenant isolation
    What it checks: Each hostname routes only to its own pod. Wrong host headers return 404 — no cross-tenant traffic leaks through the LB.
    # Positive — each hostname returns its own tenant badge curl -s http://dev.linexa.eu | grep -o '<title>.*</title>' # → <title>Linexa</title> curl -s http://dev.tenant-cfd4486.linexa.eu | grep -o 'tenant: [a-z0-9]*' # → tenant: cfd4486 curl -s http://dev.tenant-3622fab.linexa.eu | grep -o 'tenant: [a-z0-9]*' # → tenant: 3622fab # Negative — wrong Host header must NOT bleed into another tenant curl -s -o /dev/null -w "%{http_code}" \ --header "Host: dev.tenant-cfd4486.linexa.eu" \ http://<LB-IP> # → 404 (ingress drops unknown direct-IP requests) # Namespace sanity — each pod lives in its own namespace kubectl get pods -n linexa-dev kubectl get pods -n linexa-tenant-cfd4486 kubectl get pods -n linexa-tenant-3622fab
    Isolation boundary today
    GCP HTTP(S) LB enforces hostname routing — a request for an unknown host gets a 404/502. Namespaces are separate; pods on the same node share the kernel network stack.
    Stronger isolation — NetworkPolicy
    By default pods in different namespaces can still reach each other inside the cluster. Apply k8s/network-policies/tenant-isolation.yaml to each tenant namespace to drop all cross-tenant pod traffic.
    # Block cross-tenant pod-to-pod traffic kubectl apply -f k8s/network-policies/tenant-isolation.yaml -n linexa-tenant-cfd4486 kubectl apply -f k8s/network-policies/tenant-isolation.yaml -n linexa-tenant-3622fab # Verify — from inside cfd4486 pod, 3622fab should now be unreachable kubectl exec -n linexa-tenant-cfd4486 deploy/tenant-cfd4486 -- \ curl -s --max-time 3 http://tenant-3622fab.linexa-tenant-3622fab.svc.cluster.local # → connection timed out (blocked)
    Blast-radius test — uninstall one tenant and verify the others are unaffected:
    helm uninstall tenant-cfd4486 -n linexa-tenant-cfd4486
    dev.linexa.eu still works. dev.tenant-3622fab.linexa.eu still works. Zero blast radius.
